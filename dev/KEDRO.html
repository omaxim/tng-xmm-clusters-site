Kedro pipelines: the map¶

This page maps the Kedro graph onto the commands and the cluster jobs: the node graph, a table of every node with its command and job, the commands that are not nodes, and how production uses the graph. Every science step is a Kedro node that calls the SAME function as the command line (and the SLURM job that runs that command): Kedro adds the graph, the declared datasets and the parameters, never a second implementation. Production runs the cluster jobs (many workers on one node); a Kedro run of a node does the same work with the same bytes on the scale of a laptop or a login node.

User-facing instructions (what to run, inputs, outputs): docs/PIPELINE.md.

The graph¶

Generated by tngxmm viz --mermaid from register_pipelines() (the same block is in README.md; tests/unit/test_kedro_pipelines.py fails when either is stale). One box per node (<stage>.<function>), one arrow per dataset passed between nodes; cylinders are inputs no node produces. The empty ml stage is not registered. Node tags: env.<stack> (the environment the node runs in, from pipeline_registry.STAGE_ENV and NODE_ENV) and cite.<key> for the scientific references of the node (general-purpose libraries, cites.GENERIC_SOFTWARE, are in the bibliography but not tagged). viz.plot_mock_truth is registered in viz but left out of __default__ (NOT_IN_DEFAULT): it reads analysis.mock_fits. The bank’s fold node is bank.assign_linked_donor_folds. The static Kedro-Viz is built by tngxmm ledger viz --build-dir <dir> without machine paths.

Pass 1 and pass 2 of the pairing on the fit mass¶

Neither pass has a node of its own; both use the generation and fit nodes with a preset and a target list of their own (A production run from the target list to the masses).

  • Pass 1 (config.PASS1_PRESETS): tngxmm donors pass1-targets writes one view of every halo-snapshot under one reference observation. For FLAMINGO L1_m8 the 5,001 views of v1_flamingo_l1m8_pass1 are generated and fitted with short chains.

  • Pass 2 (config.PASS2_PRESETS, sim.projection = 'icosahedral6'): tngxmm donors pair-projections --assignment least-used pairs every halo-snapshot with an ok pass-1 fit with the observations of its window in redshift and fitted mass (donors/pair_projections.py) and writes its six icosahedral views, each under a different observation (donors/pair_six_views.py). v1_flamingo_l1m8_pass2 pairs with the bank, v1_flamingo_l1m8_pass2_extra with all 808 observations (donors.reference_sample = 'bank638+extra'), and its views are fitted with massfit.psf_eval = 'window' and massfit.projection = 'matrix' (The PSF on the mask window and the projection in one product: what changes, by how much, how fast). The list with the added observations is not built yet.

One graph for every simulation¶

The graph does not depend on the simulation. The preset (params:preset, kedro run --params preset=v1_flamingo) is the only thing that changes between TNG-Cluster, TNG300, FLAMINGO (L1_m10 and L1_m8), SIMBA and EAGLE; every node resolves it with get_preset. Only ingest.build_canonical_cubes knows a simulation’s files: it asks the loader registry (tngxmm.ingest.loaders: descriptor name to loader module, family default otherwise) for the loader of the preset’s descriptor and calls its ingest_run. Every other node, sim.* onward, is the same node with the same inputs, outputs, function and tags for every preset. tests/unit/test_single_graph.py registers the pipelines under each preset’s parameters and compares them, compares the catalog, and scans the source for a module outside ingest/ that branches on a simulation name or on the descriptor family (the few hits are listed in the test with their reason; they are builders of TNG target lists and documentation figures).

What differs lies in the data, not in the graph:

  • the ingest node’s dataset canonical_cubes is not an input of any other node; the generation reads the cubes (or the cube index files) from disk, selected by runtime.cube_store of the preset ('canonical' for FLAMINGO, 'index' for the TNG family, SIMBA and EAGLE), so kedro run --pipeline sim also works without the ingest node;

  • the planned snapshots of a periodic box (descriptor kind box) are those with targets, those of a zoom simulation (TNG-Cluster) every snapshot of the preset;

  • the gas conversion of the index route is the loader’s (loaders.gas_fn), so SIMBA and EAGLE apply their rules (ingest.simba, ingest.eagle) there too.

SIMBA and EAGLE are read through the TNG-format conversions on Vera, whose readme asks users to contact its author (D. Nelson) before use. That has not been done: both are internal validation runs (descriptor status: validation, which the canonical_cubes record repeats) and none of their products is for release.

Streamed cubes (FLAMINGO L1_m8)¶

The L1_m8 cubes come from the public FLAMINGO data service (hdfstream), which the login node reaches and the compute nodes do not, and a sample of 5,000 halo-snapshots is about 35 hours of streaming. The streaming is therefore not a node. It runs before the graph, on the login node, one stream at a time and resumable:

  1. python -m tngxmm.ingest.swift_remote soap <dir>: the SOAP-HBT halo table of each snapshot;

  2. internal/ledger_tests/multisim/l1m8_sample.py: the sample rule (DECISIONS, “FLAMINGO L1_m8 … sample rule stated before the streaming”; fixed seed) writes sample.csv, from which the tables of the sample are cut;

  3. python -m tngxmm.ingest.swift_remote cubes <table.csv> <cube_root> --snap S --half 5.66 per snapshot (the run script run_sample.sh of the run directory loops over the snapshots).

The result is one <cube_root>/flamingo_l1m8/cubes_<snap:03d>.h5 per snapshot with its .manifest.json: a group per halo, a subgroup per particle kind, gzip-compressed datasets in physical units, each with the sha256 of its uncompressed bytes; the manifest holds those hashes again with the particle counts and halo attributes, and the file attributes name the remote snapshot and SOAP paths and the SOAP version. The cube half-side is max(5.66 R500c, 1.001 x 3 R200c).

kedro run --pipeline ingest --params preset=v1_flamingo_l1m8,ingest.cube_root=<cube_root> then opens each file read-only and calls cube_io.verify_halos: every planned halo (the run’s targets; where the targets list has none of this simulation, every halo of the manifest) is in the file and in the manifest, marked complete, with the manifest’s particle counts and the manifest’s sha256 beside every dataset. ingest.verify_deep=true also hashes the stored arrays (reads the whole file, 170 MB per halo). A missing file or halo, or a failed check, stops the run; nothing is written or streamed. The record per run has the same keys as for any simulation, plus n_verified and the remote paths. The node needs no network, so it also runs on a compute node. The shallow check reads the metadata of about 20 datasets per halo, which is latency-bound on the project file system: 0.67 s per halo (665 halos of snapshot 78 in 443 s on a busy login node), so about an hour for the 5,000 halo-snapshots.

On a machine with the network the node can fetch what is missing itself. With ingest.stream_missing=true it streams the planned halos that the cube file lacks before the check (swift_remote.stream_missing): the SOAP table of the snapshot is read from ingest.soap_dir (default <cube_root>/flamingo_l1m8/soap) and fetched when it is not there, and the cubes are written exactly as step 3 writes them (half-side ingest.half_side_r500, cover sim.truth_sphere_r200c). Halos already in the file are not read again, so the cube root can start empty and fills with the targets of each run; an interrupted run goes on where it stopped. A halo costs about 25 s and 440 MB of transfer (median of 3,116 halos of the pass-1 sample) and 115 MB on disk. Snapshot 48, halo 24039133 streamed this way on 2026-11-25 has the sha256 of the production cube in all 20 datasets. The environment needs hdfstream beside Kedro (the flamingo_stream environment alone has no Kedro). The default is off: on the cluster the compute nodes have no network and a production run must not depend on the service being up.

A run of thousands of views is made with the jobs: the target list, the generation, the SAS source lists, the fit targets in pieces, the fit plans and the fit jobs, in that order (A production run from the target list to the masses). A full disk stops the generation, the SAS queue and the fit batch with exit code 28, and the same command continues them (When a run stops).

The campaign is the one place where “the same function” matters for every byte, so sim.generate_views does not loop over halos itself: it calls tngxmm.core.pool.run_campaign with the arguments campaign run would get (targets FILE, preset, snapshot, --source, --workers, the provenance stamp, the warm-up), and reads the results CSV and obs_meta.json back. Seeds (core.rng.ViewStreams), drop_events, the VIEW_ID headers, the view-schema columns of the results CSV and the targets’ sim column are therefore the runner’s. tests/unit/test_kedro_nodes.py checks the arguments; tests/e2e/test_kedro_fixtures.py compares a Kedro run with a campaign run of the same fixture views byte for byte.

Datasets¶

Paths come from conf/<env>/globals.yml; catalogs are conf/<env>/catalog/<stage>.yml.

  • Light, committed tables (conf/base): the obs tables (src/tngxmm/obs/catalogue/) and the donor tables (campaigns/<campaign>/, campaigns/<campaign>_max/) are both the inputs the campaign reads and the outputs of their nodes, at the paths the CLI writes. Re-running those nodes rewrites the committed files in place; git diff shows any change.

  • Heavy products under $TNGXMM_DATA: view trees <data>/campaign/<preset>/<sim>/<snap:03d>/<halo:07d>/view<v>/ (photon list, percam/, merged image and coverage, AGN list, obs_meta.json, tngref_sb_map.fits), one truth_profile.h5 per halo directory, the results CSVs results_<sim>_snap_<snap:03d>.csv, fit trees, the bank, embeddings. The catalog declares the TABLES that describe them: sim.views, sim.view_meta, sim.truth_profiles, sim.tngref_maps, instrument.products, massfit.fit_results, …

  • tngxmm.core.datasets.TableDataset: a CSV whose loaded DataFrame carries its file path (df.attrs["filepath"]), for nodes that need the FILE (the campaign runner reads the targets CSV itself; provenance hashes files).

  • tngxmm.core.datasets.ReportDataset: JSON written exactly as the CLI writes its reports (indent 1, final newline).

Parameters¶

  • params:preset is the ONE CampaignSpec preset of a run (v1; v1_tng300 with sim.targets: max for the TNG300 half of the maximal list; the TNG family is v1, v1_tng300, v1_tng100, v1_tng50, config.PRODUCTION_PRESETS, and config.PRESETS holds all twelve). The random streams of a view are keyed by the string sim.rng_campaign (v4, v4_tng300, …), the name of the committed target-list family, not by the preset. Nodes resolve the preset with tngxmm.config.get_preset, so the physics and the spec hash come from code; conf/base/parameters/<preset>.yml are the generated, readable record (make params), read by no node.

  • conf/base/parameters/pipeline.yml holds run options only (workers, paths, sampler settings of the CLI defaults). test_parameter_values_agree_with_the_preset checks that no stage restates the preset and that every option that restates a spec field equals the preset’s value; a deliberate deviation is listed in the test with its reason.

  • The donors that cannot supply a generated view (no PPS products: 0720700101) are the preset’s runtime.exclude_donors (obsid, reason), not a parameter of a node: the generation applies it when the views are planned (campaign run, sim.plan_campaign, check_donor_tables, campaign check, the realism selection and split), so the committed target lists stay the pure draw. An excluded view is recorded with the status excluded: <reason>.

  • globals.campaign names the committed campaign directories (campaigns/<campaign>/, campaigns/<campaign>_max/).

The donor tables¶

Pipeline donor_tables (not part of __default__) builds the per-donor tables of the data package ($TNGXMM_DATA/tables/, one sha256 line each in SHA256SUMS). The measuring nodes cache one JSON per donor in paths.donor_tables_work and resume; a sharded run (--params donor_tables.background.shard=k/n; Kedro splits --params on commas, so [k,n] cannot be given there) fills the cache and ends without a table, with exit status 0 and the message shard k/n done (a crash exits non-zero), the unsharded run assembles it. A cached result carries its node’s MEASURE_VERSION, the donor’s catalogue row, the calibration inputs and the listing of the donor’s products (a donor without products is measured again once they appear):

kedro run --pipeline donor_tables --nodes donor_tables.fetch_pps_archive              # the event-list cache, once
kedro run --pipeline donor_tables --nodes donor_tables.fetch_pps_archive --params donor_tables.archive.refetch_none=true   # ask again about the recorded negative results
kedro run --pipeline donor_tables --nodes donor_tables.build_donor_nh_total,donor_tables.build_fwc_reference,donor_tables.measure_mos_background,donor_tables.build_mos_background,donor_tables.build_qpb_corners   # shards: --params donor_tables.qpb_corners.shard=k/n
kedro run --pipeline donor_tables --nodes donor_tables.build_donor_background,donor_tables.build_donor_soft_ccd,donor_tables.build_donor_conditions

Every table of the pipeline (the tables measured about the donors’ clusters, donor_background, donor_soft_ccd, donor_mos_background, donor_qpb_corners; the total column donor_nh_total; the condition table), and the core offsets of donors.build_core_offsets, are saved with a provenance sidecar (<table>.provenance.json: the input files, relative to the data package or the repository, with their sha256; the commit; git_dirty). PackageTableDataset writes into the data package only from a committed, clean tree (allow_dirty: true in a catalog entry of conf/local lifts that for development) and never while TNGXMM_DATA_READONLY is set (the unit tests set it). The instrument stage, the conditions donor and the fits read the data-package copy only when the sidecar says git_dirty false, records the current MEASURE_VERSION (and, for the two corner tables, the rule of the FWC reference) and names the current guarded centre and seed tables (the core offsets: the centre table and observations.csv; the corner tables: also the anomalous-CCD table; the condition table: also the current core-offset and background tables), and when those inputs are current themselves (the centre table copied from the current seed table, which is current for the production preset; no input of the data package built from an uncommitted tree), so after new centres the core offsets and the tables measured about the cluster are built again, in the order of docs/background.md (“Donor tables measured about the cluster”). The other files of the data package a view is made from are checked and recorded per view as well (sim.data_inputs).

The realism evaluation¶

Pipeline realism (src/tngxmm/realism/, not part of __default__). The steps share files, so they are separate runs in this order ($TNGXMM_DATA/realism/, or $TNGXMM_REALISM_ROOT, holds the files). The classifier and DINO nodes (realism.embed_dino, realism.dino_c2st_report, realism.c2st_report) need scikit-learn and, for DINO, torch AND Kedro in one interpreter: the sim stack has no scikit-learn and the shared embed stack no Kedro, so they run in the embed thin venv with Kedro (TNGXMM_DEV_ROOT=$TNGXMM_SITE_ENVS environment/thin_venv.sh embed <repo> prod --with-kedro, TNGXMM_SITE_EMBED_PY); the other steps run in the sim stack. slurm/realism_frozen.sh runs the whole chain on one node. The observing conditions are donors.observing_conditions of the preset (src/tngxmm/config.py; the v1 presets set {rule: nn, n: 5, jitter: [exposure, roll, pointing]} from release 1.1.1, unset = {rule: donor}, the donor’s own; hashed only when set): the production generation, the replay (instrument.replay.conditions: null) and the frozen evaluation (realism.frozen.conditions registers the value it must be) take it from there.

kedro run --env realism --pipeline realism --nodes realism.build_split           # once; frozen
kedro run --env realism --pipeline realism --nodes realism.select_views,realism.measure_count_matching
kedro run --env realism --nodes instrument.replay_views                           # serial, about 75 s per view: shard the views table over several cores of a node
kedro run --env realism --pipeline realism --nodes realism.extract_real_features,realism.extract_mock_features,realism.embed_dino,realism.dino_c2st_report,realism.c2st_report

Add --params realism.select.donor_set=heldout to select and --params realism.mode=frozen to the last run for the one frozen evaluation.

Parameters merge key by key (merge_strategy: soft, src/tngxmm/settings.py): an environment states only what it changes; lists and scalars are replaced, a mapping is merged. key: {} therefore changes nothing; an environment that must clear a mapping writes key: null. tests/unit/test_kedro_environments.py lists what each environment changes and refuses an empty-mapping override.

Kedro is an overlay of the stage environments (environment/thin_venv.sh <sim|massfit|embed> <worktree> <id> --with-kedro); a stage runs in its own environment: obs, donors, sim, instrument, photometry, bank in the sim stack; massfit, viz and the closure grid’s fits in the massfit stack (XSPEC); embed in the embed stack. Telemetry is off (plugin not installed, KEDRO_DISABLE_TELEMETRY=1, .telemetry says consent: false).
