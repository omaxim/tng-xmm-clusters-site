tngxmm.ingest.pipeline¶

Kedro pipeline of stage ingest: the canonical cubes of the planned runs.

One node:

sim.campaign_plan + sim.mock_cutouts ─build_canonical_cubes─> canonical_cubes
build_canonical_cubes per planned run, the canonical cubes of its target halos under

params:ingest.cube_root (<cube_root>/<sim>/cubes_<snap:03d>.h5 and cubes_<snap:03d>.manifest.json). The node does not know a file format: it resolves the preset’s descriptor and calls ingest_run of that simulation’s loader (tngxmm.ingest.loaders):

  • TNG-Cluster, TNG300/100/50 (tngxmm.ingest.tng) and the TNG-format conversions of SIMBA and EAGLE (tngxmm.ingest.simba, tngxmm.ingest.eagle, descriptors *_tngformat; their Subfind catalogues supply the halos of the original runs): through the cube of the mock-cutout stage (tngxmm.ingest.cli.ingest_tng_snapshots(), the command campaign ingest);

  • FLAMINGO L1_m10 (tngxmm.ingest.swift): python -m tngxmm.ingest.swift in the interpreter of params:ingest.swift_python (an HDF5 that reads the lossy-compressed datasets);

  • FLAMINGO L1_m8, SIMBA and EAGLE from their original snapshots (tngxmm.ingest.swift_remote, tngxmm.ingest.simba_remote, tngxmm.ingest.eagle_remote): the cubes are streamed from the data services (hdfstream, HTTP range requests) by a step before the graph (below); the node opens them read-only and checks the planned halos against the manifest (tngxmm.ingest.cube_io.verify_run()).

cube_root null: nothing is written or checked (the generation reads the snapshot through the index files, runtime.cube_store = 'index').

Remote cubes. The data service is reached from the login node only (the compute nodes have no network), and a sample is tens of hours of streaming, so the streaming is not a node. It is run first:

python -m tngxmm.ingest.swift_remote soap <out_dir>                    # SOAP-HBT halo tables per snapshot
python internal/ledger_tests/multisim/l1m8_sample.py ...               # the sample rule (seed fixed there)
python -m tngxmm.ingest.swift_remote cubes <table.csv> <cube_root> --snap S --half 5.66
python -m tngxmm.ingest.simba_remote <snap> <cube_root> <index_dir> --halo ID ...   # SIMBA, GIZMO over HTTP
python -m tngxmm.ingest.eagle_remote <snap> <cube_root> <index_dir> --rows rows.json  # EAGLE, hdfstream

(run_sample.sh of the L1_m8 run loops the last command over the snapshots; resumable, halos already in a cube file are skipped). A cube file holds one group per halo with a subgroup per particle kind; every dataset is gzip-compressed and carries its sha256 (of the uncompressed bytes in C order); the manifest repeats the sha256 of every dataset, the particle counts and the halo attributes, and the file attributes name the remote snapshot and SOAP paths and the SOAP version (tngxmm.ingest.cube_io). The sample rule fills the (mass, redshift) plane of the real pool with about 5,000 halo-snapshots (docs/dev/DECISIONS.md, “FLAMINGO L1_m8”). The node then emits the same canonical_cubes record as for any other simulation, after tngxmm.ingest.cube_io.verify_halos(): the planned halos (the targets of the run, or every halo of the manifest where the targets list has none of this simulation) are in the file and marked complete, and the sha256 stored beside each dataset equals the manifest’s (about 0.7 s per halo, metadata reads on the project file system); ingest.verify_deep also hashes the data (reads the whole file). A missing file or halo, or a failed check, stops the run. With ingest.stream_missing the planned halos that the file lacks are streamed first (tngxmm.ingest.swift_remote.stream_missing(); needs the network and hdfstream), so a run on a machine with the network fetches the cubes of its own targets; the record gains n_streamed.

A record of canonical_cubes: preset, snap, family, loader (module), status (the descriptor’s: production or validation), n_halos and, for streamed cubes, n_verified and the remote paths.

The generation reads the cubes when runtime.cube_store is ‘canonical’ (campaign run --cube-root); run kedro run --pipeline ingest before --pipeline sim in that case (the generation does not take this node’s output as an input, so that kedro run --pipeline sim keeps working on the index files).
